## 実装結果

- Storageの保存完了イベントから、サーバー専用のattachmentExpirationsへ期限・bucket・storagePath・世代番号・関連文書パスを登録する。Firestore保存前にアプリが終了した未参照ファイルも保持期限後に回収する。画像・PDFを従来どおり扱う。
- 日報12か月、カレンダー3か月を維持。有効な既存expiresAtを使用し、期限情報がない旧画像はuploadedAt／StorageのtimeCreatedから月末・うるう年を考慮して補完する。既存サービスと同じUTC計算。
- 毎日03:00 JSTのdeleteExpiredCalendarAttachmentsを、nextAttemptAtの期限到来分クエリへ変更。Storage全件一覧・全画像メタデータ確認・チーム全予定の取得を廃止する。対象の日報・予定を直接参照する。
- 1回最大1,000件・5並列・450秒を目安に区切り、残りは次回へ残す。既存の512MiB・540秒設定を維持。失敗対象は次回試行を1時間後へ移し、後続対象の処理を継続。Schedulerの再試行は3回・1時間間隔。
- Storage削除後、現在の参照先すべてから添付情報を除去し、期限登録を削除するFirestoreトランザクションを実行。途中失敗は登録を残し、Storageが既に消えていても再試行で添付情報を修復する。本文・コメント・他添付を保持する。
- 複数日予定の分割でStorageパスを移さず画像参照が別予定へ移る場合、新しい参照先を記録する。通常保存や本文・コメントの更新では追加のStorage読取を行わない。
- Storage削除に世代番号とメタデータ世代の一致条件を指定。置き換え・期限延長を確認する。新アプリは添付にstorageGenerationを保存し、旧アプリの添付は期限値も照合して将来の参照を保持する。
- 期限管理はクライアント許可がないトップレベルコレクション。既存ルールで読取・書込不可。単一フィールド索引を使うため、Firestore／Storageルールと複合インデックスの変更は不要。

## 本番反映・既存画像移行の順序（未実施）

Functions反映と移行は別途承認後に行う。最初にFunctionsを一括deployすると、移行前に定期処理が切り替わるため、以下の順序を守る。

1. 実際のデフォルトStorage bucket名・所在地・サービスアカウント権限を確認。Storageトリガーは現在asia-northeast1設定で、bucketと互換の所在地が必要。実Storageイベントの配信と再試行を検証環境で確認する。
2. registerAttachmentExpiry、trackCalendarAttachmentReferencesのみdeploy。新規保存・予定分割の登録を確認し、既存の定期処理は旧版のまま残す。
3. 移行CLIをdry-runで実行。Firebase CLIのloginとAdmin SDKのApplication Default Credentialsは別なので、権限のあるADCを準備する。bucket名を明示し、認証情報を表示しない。
4. 結果確認後、別チェックポイントで--applyを指定し、同じコマンドを繰り返してphaseがcompleteになるまで進める。Storage2種類を200件ずつ登録後、既存clubEventsを200文書ずつ走査して分割先を補完する。移行処理は画像削除や予定・日報更新を行わない。
5. invalidがあればメタデータを確認・補正して必要な移行を再実行する。missingは一覧取得後に消えた画像や削除済み参照を含む。保存完了トリガーの未処理・失敗も解消する。
6. 移行完了後にdeleteExpiredCalendarAttachmentsのみdeployし、03:00 JSTの処理・件数ログ・期限前保持を確認する。
7. 世代番号保存を次の通常アプリ配布へ含める。従来アプリも保持期限と操作方法は同じで動作する。

## 負荷と追加費用の見込み

14,580添付・月1,260件期限到来の管理シートモデルでは、定期処理のStorageメタデータ確認は月437,400回から約1,260回へ減る。予定分割では別途対象画像を確認する。料金・実行時間の実測結果ではない。

追加されるのは保存完了トリガー、カレンダー書込トリガー、期限管理の読み書き。通常の1画像につき初回登録1読取・1書込。期限到来時はクエリ1読取＋登録再確認1読取＋完了トランザクションの登録1読取・親文書読取、登録削除1書込・添付更新最大1書込が目安。登録・期限到来とも月1,260件で親文書1件なら、月約6,300読取・最大3,780書込が追加／置換の目安。旧処理でも親文書更新は発生していたため純増ではない。分割先、再試行、手動削除済み登録で増減する。

毎日のStorage全件走査・チーム全予定取得は不要になる。一度の移行には全画像一覧・期限登録・既存予定読取が発生する。1日1,000件を超える滞留は複数日に分けて処理される。CPU・メモリ時間と請求額は本番の関数別実績で確認する。
