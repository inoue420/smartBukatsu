## 目的と合意した仕様

Cloud Schedulerの4ジョブを3ジョブへ減らす。前段の調査で、同時刻の戦術ノート回収と問い合わせ削除は再試行設定が異なるため、両方が再試行なしの「通知削除＋問い合わせ削除」を統合する案を採用した。

| 処理 | 変更前 | 変更後のローカル定義 |
| --- | --- | --- |
| 予定・日報の添付期限切れ削除 | 毎日03:00 JST | 維持 |
| 戦術ノートの未使用添付・下書き回収 | 毎日03:30 JST・再試行3回 | 維持 |
| 問い合わせ期限切れ削除 | 毎日03:30 JST | 通知削除と毎日03:45 JSTへ統合 |
| 通知期限切れ削除 | 毎日03:45 JST | 公開名deleteExpiredNotificationsを維持 |

- 問い合わせの期限判定は、Schedulerの元のscheduleTimeから15分引いた時刻。通常の03:45 JST実行では同日03:30 JSTとなる。
- 実行が遅延しても、実際の開始時刻で削除対象を増やさない。将来の時刻が渡された場合も、判定時刻は実行時点を超えない。
- 問い合わせのresolved／legalHold判定、100件ずつの取得、recursiveDeleteによる子データ削除、保護対象しかないページで停止する既存の動作を維持。
- 通知削除の本文は処理を変えず通常の非同期関数として再利用。90日保持、1回合計400件上限、未読集計のトランザクション補正を維持。
- 両処理をPromise.allSettledで並列実行。片側の通常例外・同期例外でも他方を実行し、両方の終了後に全体の失敗を返す。
- 個別の成否と処理時間を記録。通知・問い合わせ内容やAPIエラー本文はログへ含めない。
- 統合先は1vCPU・1GiB・最小インスタンス0・540秒・retryCount 0・maxRetrySeconds 0。
- 通常の通知送信、認証、Rules、既存データ構造、保存期限の設定処理は変更しない。
