## 今回の範囲

購読方式を変える前に開発用アプリで取得量を把握する。現在のクエリ、購読開始条件、解除タイミング、データ変換、認証・権限失効処理は維持する。画面単位の購読停止、投稿・日報のページング、予定の期間制限は、同一データ・操作での計測結果を踏まえた次段階とする。この段階だけで管理番号全体を完了としない。

`__DEV__` が true のときだけ計測する。通常のリリースバンドルでは計測せず、設定画面にも表示しない。開発用のネイティブアプリでもリリースJSでは無効になる。パッケージ、アプリバージョン、EAS設定、Firebase Rules / Functions / インデックスは変更しない。

診断欄の表示・更新・コピーは、Android / iOSでSharpRiseデバッグ部への加入を確認できたユーザーだけに限定する。既存の広告診断の加入判定を共有し、チームの招待コードと所属メンバー情報で確認する。デバッグ部を現在選択中である必要はない。判定中・未加入・取得失敗時とWebでは非表示。設定へ戻るときや所属一覧が変わったときに既存の判定が再実行される。判定が不許可になると診断テキストと展開状態をクリアする。加入状態だけのリアルタイム監視は追加しないため、他のチームを選択中の外部からの所属解除は設定の再表示等で確認する。端末内計測自体は開発時の起動から継続し、加入判定のための読取りは追加しない。

計測名は16種類に固定し、文書内容・ユーザーID・チームID・パス・エラーメッセージを保存しない。取得したsnapshotも保持しない。開始・終了の履歴は最新60件に制限し、集計は起動後の累計とする。通常ログへの出力、永続保存、Firestoreへの送信、自動コピーは行わない。コピーはユーザー操作時だけ行う。

設定画面のフォーカス時、計測欄を開くとき、更新・コピーの操作時に現在値を取得する。各snapshot到着時の画面再描画や定期ポーリングは追加しない。集計で例外が起きても既存のデータ受信コールバックへsnapshotを渡し、計測失敗回数だけを記録する。

## 指標の読み方と制限

- **開始・終了・継続中:** ラッパー呼出し／解除の回数。既存エラーハンドラに渡される購読エラーも終了として数える。終了後の解除を重複計上しない。エラーハンドラがない `authUser` はSDKの既定エラー処理を維持するため、エラー終了を捕捉せず、解除まで継続中に含まれる。
- **初回文書数:** 各購読の最初の通知の文書数。キャッシュ由来／サーバー由来に分ける。初回の `docChanges().added` は追加数にも計上しない。空の結果は初回通知1回・0文書。
- **追加・変更・削除:** 2回目以降のクエリ通知の `docChanges()` の件数。単一文書は存在状態の変化で追加・削除を判別し、存在し続ける通知は変更とする。この変更数にはメタデータ由来の通知が含まれる場合がある。
- **サーバー初観測:** 各購読で最初に受け取った `fromCache === false` の通知件数・文書数。キャッシュ先行時の補助指標であり、初回・差分と加算しない。既存の `includeMetadataChanges` 設定を変えていないため、キャッシュとサーバーの内容が同じ場合、サーバー通知を観測できず0のままの場合がある。0は未読・未接続を意味しない。
- **書込み未確定:** `hasPendingWrites` が立つ通知回数。キャッシュ／サーバー集計と重なる別指標。
- **対象外:** `getDoc` / `getDocs` の単発読取り、サーバーの再接続内部処理、セキュリティルールやインデックスによる課金等。特に `teamMembers` は名前のないメンバーについて追加の `getDoc` を行う既存処理があり、その読取りはこの購読計測に含まれない。
- **課金との違い:** ローカル更新やクエリ対象から外れた文書も差分になる。リスナー本数・snapshot件数・文書数の合計を課金読取り数や削減率として扱わない。Firestore全体の使用量と併せて評価する。
- **セッション:** チーム切替・ログアウトでも固定名の累計を維持する。チーム別／ユーザー別にデータを保持しない。新しい比較試行はFast Refreshではなくアプリを再起動して開始する。

## 実機での比較手順（Android / iOS）

1. 開発クライアントとMetroの開発バンドルを使用する。SharpRiseデバッグ部の加入者で、設定 →「Firestore購読の計測（開発用）」が表示されることを確認する。加入済みなら別チームを選択中でも表示され、未加入者・判定中・取得失敗時・Web・リリースJSでは表示されないことを確認する。脱退後に設定へ戻る場合と、未加入アカウントへ切り替える場合は非表示になり、以前の診断テキストが残らないことを確認する。
2. 許可された検証用アカウント・同じ検証データを使う。アプリを再起動し、起動直後の操作・時刻を控える。設定で結果をコピーし、基準値として端末外へ手動で記録する。診断欄への遷移も比較前後で同じにする。
3. ホーム → 日報 → カレンダー → 動画 → 設定を同じ順序・回数で往復。各操作後の累計と前回との差、開始・終了履歴を確認する。
4. バックグラウンドからの復帰、通信断・再接続、チーム切替、ログアウト・再ログインを個別に試す。既存の解除対象が終了し、新しい購読の開始・初回文書数が増えることを確認する。
5. 別の検証端末から許可された検証データを追加・変更・削除し、差分と画面反映を確認する。通知からの遷移、ホーム件数・未読バッジ、日報の警告、固定・過去投稿、複数日予定、検索を確認する。
6. 所属解除・権限失効のケースは検証用データで別途許可のある場合に実施する。これまでどおりアクセス失効が検知され、旧チームの内容が表示され続けないことを確認する。今回この既存動作を修正したわけではない。
7. 計測失敗が0であること、コピー内容に個人情報や文書内容がないことを確認する。リリースJSでは診断欄が非表示であることを確認する。
8. 同じ時間幅のFirestore全体使用量と照合する。負荷の大きい購読を選び、停止条件・ページング・期間クエリを別途提案する。変更後は同じ操作・データ・キャッシュ条件で比較する。キャッシュあり／なしの試行を混ぜない。

実機の実測、Firebase使用量の取得、データ更新、EASビルド・配信はこのローカル実装では実施しない。
