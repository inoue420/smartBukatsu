# AGENTS.md

## 1. このファイルの目的

このリポジトリでCodexを使用する際の作業ルールを定めます。

Codexは、VS Codeで開いているローカルワークスペース内のファイルを確認・調査できます。
ただし、**ファイルの変更、作成、削除、コマンドによる変更、Git操作など、プロジェクトへ影響する操作は、必ず事前にユーザーの承認を得てください。**

承認を得るまでは、調査、分析、説明、変更案の提示だけを行ってください。

---

## 2. プロジェクト概要

- プロジェクト名：SMARTBUKATSU
- 開発環境：VS Code
- フレームワーク：Expo / React Native
- ビルド・配布：EAS
- 対応OS：Android / iOS
- バックエンド：Firebase
- ソース管理：Git / GitHub
- 開発体制：オーナー、バイト生、Codexによる共同開発
- GitHubではPull Requestを使用する

## 3. 変更点管理シートと管理番号ベースの標準フロー

### 3.1 変更点管理シート

SMARTBUKATSUの変更点管理シートは次のファイルです。

```text
https://docs.google.com/spreadsheets/d/1AqG1eDzzgD6uEy3E_jb06StlTJZszS-jBJj-_s62hz4/edit
```

Drive上のファイル名：

```text
SmartBukatsu_改訂履歴管理シート
```

主なシート：

- 改訂履歴
- 入力候補

管理ファイルはGoogle スプレッドSheetsです。

ユーザーから管理番号が指定された場合は、Google Driveプラグインを使用して対象管理番号の行を参照してください。

原則として管理シート全体を毎回再整理する必要はありません。指定された管理番号の行と、その理解に必要な見出し・候補値だけを確認してください。

対象行が見つからない場合は、次の順で確認してください。

1. 管理番号の完全一致
2. 前後の空白
3. 全角・半角の差
4. 改定タイトルとの部分一致

対象行を特定できない場合は、その旨をユーザーへ報告してください。別の項目を推測で代用してはいけません。

完全な読み取りができない場合は、確認できた内容と確認できなかった列・セルを明示してください。

管理シートのダウンロード、変換、複製、別形式保存が必要な場合は、事前にユーザーの承認を得てください。

### 3.2 管理番号だけが指定された場合

新しいCodexチャットで、ユーザーが次のように管理番号だけを指定する場合があります。

```text
SB-20260724-001を対応してください。
```

または：

```text
管理番号 SB-20260724-001
```

この場合、管理シートURLや基本ルールをユーザーへ再入力するよう求めず、本`AGENTS.md`に従って標準フローを開始してください。

### 3.3 標準フロー：初期確認

管理番号を受け取ったら、まず変更を行わずに次を確認してください。

1. 本`AGENTS.md`
2. 指定された管理番号
3. 現在のGitブランチ
4. `git status`
5. 未commit変更
6. 未追跡ファイル
7. 管理シートの対象行
8. 対象行の要約

最初の応答は、原則として次の趣旨にしてください。

```text
管理番号「SB-XXXXXXXX-XXX」を対象に、AGENTS.mdに従って調査を開始します。

まず以下を行います。
- 管理シートの対象行確認
- Git状態確認
- 現在のコードとの照合
- 仕様上の不明点と実装案の整理

この段階では、コード変更、Git操作、パッケージ変更、
管理シート更新、Firebase/EAS操作は行いません。
```

### 3.4 標準フロー：コードとの照合

対象項目について、次を調査してください。

1. 現在の実装状況
2. 管理シートの要望との差分
3. 関連ファイル
4. 関連する画面遷移
5. Firebase・認証・権限への影響
6. Androidへの影響
7. iOSへの影響
8. Webへの影響がある場合はその内容
9. 既存機能への影響
10. 仕様の曖昧さ・不足・矛盾
11. 実装方法の選択肢
12. 推奨案
13. テスト方法
14. 元に戻す方法

管理シートの改定区分と、実際のコード上の影響範囲が異なる場合は、その差を明示してください。

### 3.5 標準フロー：承認依頼

コード変更が必要な場合は、次の形式で実装計画を提示し、必ずユーザーの承認を得てください。

```text
【変更承認のお願い】

管理番号：
変更タイトル：
目的：
変更予定ファイル：
変更内容：
影響範囲：
Androidへの影響：
iOSへの影響：
Firebaseへの影響：
実行予定コマンド：
テスト方法：
元に戻す方法：
注意点：

上記の内容で実装してよいでしょうか。
承認をいただくまでは変更を行いません。
```

仕様上の判断が必要な場合は、承認依頼より先に質問してください。

### 3.6 標準フロー：承認後の実装

ユーザーが明示的に承認した範囲だけを実装してください。

- 必要最小限の変更に限定する
- 承認されたファイルと内容を基本範囲とする
- 計画外の変更が必要になったら停止して再承認を得る
- 関係のないリファクタリングをしない
- 関係のない自動整形をしない
- 他の開発者の未commit変更を上書きしない
- Firebaseや認証に影響する変更を推測で行わない

### 3.7 標準フロー：検証と報告

変更後は、commitやpushを行う前に次を報告してください。

1. 変更したファイル
2. ファイルごとの変更内容
3. `git diff`の要約
4. 実行したコマンド
5. 実行したテスト
6. テスト結果
7. Androidへの影響
8. iOSへの影響
9. Firebaseへの影響
10. 未解決事項
11. 手動確認が必要な項目
12. 元に戻す方法
13. commit・push・PR・管理シート更新が未実施であること

### 3.8 管理シートへの記録

コード変更と動作確認が完了したら、管理シートへの記載案を作成してください。

ユーザーから明示的な書き込み承認を受けるまでは、管理シートを直接更新しないでください。

記載案には、利用可能な列に応じて次を含めてください。

- 管理番号
- 対応日
- ステータス
- 担当者
- 対象バージョン
- 実装内容
- 変更ファイル
- テスト内容
- テスト結果
- Androidへの影響
- iOSへの影響
- Firebaseへの影響
- 未解決事項
- ブランチ名
- commit ID
- Pull Request URL

対応する列がない情報は、備考欄などへ勝手に統合せず、記載場所をユーザーへ確認してください。

### 3.9 作業単位

原則として次の単位で作業してください。

```text
1管理番号
＝ 1Codexチャット
＝ 1作業ブランチ
＝ 1Pull Request
```

関連性が高く、ユーザーが明示的にまとめることを承認した場合に限り、複数の管理番号を同一作業へ含められます。

## 4. 最重要ルール

### 4.1 変更前の承認は必須

以下の操作は、どれだけ小さな変更でも、実行前に必ずユーザーの承認を得てください。

- 既存ファイルの編集
- 新規ファイルの作成
- ファイル名の変更
- ファイルやフォルダの移動
- ファイルやフォルダの削除
- パッケージの追加、更新、削除
- 設定ファイルの変更
- 自動整形による変更
- コード生成
- Gitのcommit、revert、reset、stash
- ブランチの作成、変更、削除
- GitHubへのpush
- Pull Requestの作成、更新、マージ
- EAS、Expo、Firebaseなどの外部サービスに影響する操作
- データベース、認証、ストレージ、セキュリティルールの変更
- シェルコマンドやスクリプトによるファイル変更

変更が必要な場合は、実行前に次の内容を提示してください。

1. 変更の目的
2. 変更予定のファイル
3. 変更内容の要約
4. 想定される影響
5. 元に戻す方法
6. 実行予定のコマンド
7. ユーザーの承認待ちであること

承認を得るまでは変更を実行しないでください。

### 4.2 調査は許可

次の操作は、プロジェクトを変更しない範囲で実行できます。

- ワークスペース内のファイル閲覧
- コード検索
- Gitの状態確認
- Gitの差分確認
- Gitの履歴確認
- 設定内容の確認
- エラーログの分析
- コード構成の説明
- 変更案の提示
- 問題箇所の特定
- 実行すべきコマンドの提案

ただし、閲覧コマンドであっても、外部サービスへのアクセスや認証を伴う場合は事前確認してください。

## 5. 作業開始時の確認

作業開始時は、可能な範囲で次を確認してください。

- 現在のGitブランチ
- `git status`
- 未commitの変更
- 未追跡ファイル
- ユーザーや他の開発者による作業途中の変更
- 対象機能に関係するファイル
- Expo SDK、React Native、主要パッケージの現在のバージョン

既存の未commit変更がある場合は、それを上書き、削除、整形、移動しないでください。

自分が作成したものではない変更を発見した場合は、その内容をユーザーへ報告し、扱いについて確認してください。

## 6. 変更方針

承認後に変更する場合も、次のルールを守ってください。

### 6.1 必要最小限の変更

- 指示された目的に必要な範囲だけを変更する
- 関係のないリファクタリングを行わない
- 関係のない命名変更を行わない
- 関係のない整形を行わない
- 大量のファイルを一括変更しない
- 既存仕様を推測だけで変更しない
- AndroidとiOSの両方への影響を確認する
- Firebaseの既存データ構造との互換性を考慮する

### 6.2 段階的に変更する

大きな変更は一度に行わず、次のように分割してください。

1. 現状調査
2. 変更案の提示
3. ユーザー承認
4. 最小単位の変更
5. 差分確認
6. テスト
7. 結果報告
8. 次の変更について再承認

一度の承認を、関連の薄い追加変更への包括的な許可として扱わないでください。

### 6.3 不明点は勝手に補完しない

仕様が不明確な場合は、実装を進めずに次を示してください。

- 不明点
- 考えられる選択肢
- 各選択肢のメリットとデメリット
- 推奨案

## 7. Git運用

### 7.1 ブランチ

- `main`へ直接commitしない
- `main`へ直接pushしない
- `develop`へ直接commitしない
- `develop`へ直接pushしない
- 作業ごとに専用のfeatureブランチを使用する
- バイト生、オーナー、Codexで同じ作業ブランチを同時に使用しない

Codex用ブランチの例：

```text
feature/codex-login-improvement
feature/codex-team-switching
fix/codex-android-build-error
```

ブランチ作成も事前承認を得てください。

### 7.2 commit

commitはユーザーの明示的な承認がある場合だけ実行してください。

commit前には次を提示してください。

- 変更ファイル一覧
- `git diff`の要約
- テスト結果
- commitメッセージ案

1つのcommitには、原則として1つの目的だけを含めてください。

### 7.3 push・Pull Request

次の操作はユーザーの明示的な承認なしに行わないでください。

- `git push`
- force push
- Pull Request作成
- Pull Request更新
- Pull Requestのマージ
- GitHub上のIssueや設定変更

Codexは原則として、ローカルでの変更と検証までを担当します。

### 7.4 禁止するGit操作

次の操作は、ユーザーから具体的な指示がない限り実行しないでください。

```text
git reset --hard
git clean -fd
git clean -fdx
git push --force
git push --force-with-lease
git rebase
git filter-branch
git filter-repo
```

変更を戻す必要がある場合は、まず安全な方法を説明してください。

## 8. Expo・EAS運用

### 8.1 勝手に変更しない項目

次の項目は、明示的な承認なしに変更しないでください。

- Expo SDKのバージョン
- React Nativeのバージョン
- `app.json`
- `app.config.js`
- `eas.json`
- Android package名
- iOS bundle identifier
- version
- buildNumber
- versionCode
- scheme
- plugins
- permissions
- entitlements
- deep link設定
- AdMob関連設定

### 8.2 実行前承認が必要なコマンド

次のコマンドは、実行前に必ず承認を得てください。

```text
npm install
npm uninstall
npm update
npx expo install
npx expo prebuild
npx expo run:android
npx expo run:ios
eas build
eas submit
eas update
eas credentials
```

`package.json`やロックファイルを変更する可能性があるコマンドは、すべて変更操作として扱ってください。

### 8.3 本番操作は禁止

ユーザーからその操作を明示的に依頼されない限り、次を実行しないでください。

- productionビルド
- App Store Connectへの提出
- Google Play Consoleへの提出
- OTAアップデート配信
- 本番バージョン番号の更新
- 証明書や署名情報の更新

## 9. Firebase運用

次の操作は、明示的な承認なしに実行しないでください。

- Firebaseへのdeploy
- Firestoreデータの追加、更新、削除
- Authenticationユーザーの変更
- Storage内ファイルの変更
- Cloud Functionsのdeploy
- Firestore Rulesの変更
- Storage Rulesの変更
- Firebase Hostingのdeploy
- インデックスの作成や削除
- 本番環境への接続設定変更

特に、次のコマンドは勝手に実行しないでください。

```text
firebase deploy
firebase use
firebase functions:delete
firebase firestore:delete
```

セキュリティルールを変更する場合は、変更前後の差分、影響範囲、想定ユースケースを提示してください。

## 10. 秘密情報・認証情報

次の情報を表示、記録、変更、commit、pushしないでください。

- `.env`
- `.env.local`
- `.env.production`
- APIキー
- サービスアカウント鍵
- Firebase Admin SDK秘密鍵
- Appleの`.p8`ファイル
- Android keystore
- keystoreのパスワード
- EASアクセストークン
- GitHubトークン
- Google Playサービスアカウント鍵
- 決済サービスの秘密鍵
- 個人情報
- 本番ユーザーデータ

秘密情報を発見した場合は、値を出力せず、ファイル名と問題の種類だけをユーザーへ報告してください。

秘密情報をログ、コメント、テストコード、サンプルコードへ書かないでください。

## 11. パッケージ管理

パッケージの追加、更新、削除は、必ず事前承認を得てください。

提案時は次を説明してください。

- パッケージ名
- 導入理由
- 現在のExpo SDKとの互換性
- Androidへの影響
- iOSへの影響
- ネイティブビルドが必要か
- Expo Goで動作するか
- dev-clientが必要か
- EAS再ビルドが必要か
- 代替手段
- ライセンスや保守状況

主要パッケージを、問題解決と関係なく一括更新しないでください。

## 12. テストと検証

テストコマンドも、ファイルや設定を変更する可能性がある場合は事前承認を得てください。

承認後、変更内容に応じて可能な範囲で次を確認してください。

```text
npx expo-doctor
npx tsc --noEmit
npm test
npm run lint
npx expo export --platform android
npx expo export --platform ios
```

ただし、実際のプロジェクトに存在しないスクリプトを勝手に追加しないでください。

テスト失敗時は、失敗を隠さず次を報告してください。

- 実行したコマンド
- 成功または失敗
- エラー内容の要約
- 原因の推定
- 今回の変更が原因か
- 未解決事項

変更を実施した場合は、最後に次を報告してください。

1. 変更したファイル
2. ファイルごとの変更内容
3. 変更していない重要ファイル
4. 実行したコマンド
5. テスト結果
6. Androidへの影響
7. iOSへの影響
8. Firebaseへの影響
9. 既知の問題
10. 手動確認が必要な項目
11. 元に戻す方法
12. commit・push・PRが未実施かどうか

変更が承認されなかった場合は、ファイルを変更せず、提案内容だけを報告してください。

目的：

## 15. このルールの優先順位

この`AGENTS.md`のルールは、このリポジトリ内でのCodex作業に適用します。

特に次の原則を最優先とします。

1. 変更前に必ず承認を得る
2. 承認前は読み取り・調査だけに留める
3. 必要最小限の変更にする
4. `main`と`develop`を直接変更しない
5. push、PR、マージ、本番公開は勝手に行わない
6. 秘密情報を扱わない
7. 問題があれば安全に戻せる状態を保つ
